## Done
- **M4.1** Found on the way: the in-app chat loop ran write/build tools with **no approval at all**, alongside web fetch. Now one `ToolCallGuard` serves the chat and every MCP connection: output of untrusted tools (`web_fetch`, `web_search`; later MCP-client tools) is fenced in `<untrusted source=…>` (closing tag neutralised) and taints the conversation; while tainted, write/exec **always ask**, saved "Always allow" is ignored and "Always allow this" is not offered or remembered; the sheet says which outside sources are in the conversation; a new conversation clears the taint; the system prompt tells the model not to follow instructions inside `<untrusted>`. Outside MCP apps behave as before (write/exec always ask unless remembered) plus the taint rule. A clean in-app conversation runs its tools without prompts as before. Not verified in the running app yet (M4.4).
- **M4.2** Servers are user-added programs (Settings → "Tools from other MCP servers": name, command, arguments), started over stdio with a Homebrew-aware PATH; config in `Application Support/VibeCockpit/mcp-servers.json` (0600). Rules: tools are exposed as `<server>__<tool>` so a server can't shadow `write_file` etc.; descriptions are capped at 400 chars and tagged `[from <server>]` (they're text the model reads); results capped at 64k chars; every call is scope `toolsExec` and **always asks** (even in a clean conversation, and a saved "always" for the chat doesn't apply — the prompt names the server); output is fenced + taints the conversation. One server failing (bad command, exits at once, 20 s timeout) doesn't affect others. `MCPToolHost` now asks for the external tool list on every `tools/list`/call, so servers that start later appear without reconnecting. Tested against a real stdio server (Python) for listing, shadow-name, description cap, ask-every-time, fencing, taint, failure isolation. Known gap: a server that crashes *after* starting isn't marked failed until restart. Not verified in the running app yet (M4.4).
- **M4.3** Settings → Projects: add folders (NSOpenPanel), persisted in `workspaces.json`. Each project gets its own git snapshot manager, **own search index** (`indexes/<id>.db`), and own `WorkspaceBoundary`, so search results and file access can't cross projects. The MCP tools (`search_code`, `read_file`, `write_file`, `run_build`, snapshots, `index_workspace`) are now routed: they gain a `workspace` argument (project id or name, any case); with one project it's optional, with several it's **required** and declared in `required` — a write never lands in a project by guess; the approval prompt is prefixed `[project]`. New `list_workspaces` tool. A folder that fails to open fails alone. The app's own start folder, when it's a git checkout, is added automatically. The legacy single-workspace attach in `startup` is gone (the in-app chat's own RAG index is unchanged). One shared build-helper connection, opened on first use. **Side fix:** several built-in tools declared their input schema as a bare property map (not valid JSON Schema, no `type`), so MCP clients and cloud models could mis-handle them; `Tool.withValidSchema` now normalises them in `tools/list` and for model tool definitions. Boundary isolation between projects relies on the existing per-runtime `WorkspaceBoundary` (unit-tested earlier); routing itself is tested with stub tools. Not verified in the running app yet (M4.4).
- **M4.4** Built app, fake home, two git projects + a real stdio external server, driven over the app's MCP socket. **Verified live:** `tools/list` shows `read_file` with valid JSON Schema (`type: object`, `required: [workspace]`, props incl. `workspace`) and the external tool as `fake__write_file` next to the built-in `write_file` (no shadowing); `list_workspaces`; `read_file` with `workspace: alpha|beta` returns each project's own file; missing `workspace` → error naming the projects; unknown project → error; **alpha's tool reading beta's file → "Path outside workspace"**; the external tool's result comes back wrapped in `<untrusted source="fake__write_file">`; the external tool call raised an approval request naming the server (`mcp:fake`). The start folder (git checkout) was auto-added as a third project, as designed.
- **Finding — something auto-answers the approval sheet.** In every run the sheet was answered ~2 s after it was queued, with no click from me: with "Always allow this" present it chose that; with that button removed it chose "Allow once". The trace shows the answer coming from the sheet's own button closure (i.e. a UI press), not from app code, and it is deterministic (~2.3 s), so it is not a person. The likely source is desktop automation on this machine (possibly the computer-use grant for this app; not confirmed), which auto-presses the most permissive button of a dialog. Consequences: (1) **"Don't allow" and the 120 s timeout still can't be observed live** (unit-tested only); (2) any auto-clicker defeats the approval sheet — this is a property of the machine, not the app, but worth knowing; (3) M2.8's "Allow once / Always allow observed working" was this same effect — it shows the buttons work, not that a person chose. To settle it: run the check with computer-use access revoked for this app and watch the sheet stay up.
